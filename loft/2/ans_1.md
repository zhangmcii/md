# 面试口述稿

下面这份是基于 `ans.md` 压缩出来的口述版本，分成：

- 3 分钟版：适合面试开场、项目介绍、第一轮自我展开
- 8 分钟版：适合面试官继续追问“你详细讲讲这个项目架构”


## 3 分钟版

如果让我用比较工程化的方式介绍这个项目，我会说它的价值不在于做了多少 CRUD，而在于我把一个典型的 Flask 单体后端，逐步重构成了一个更接近 Clean Architecture 的结构。

这个项目原来的形态比较像 Flask 官方常见写法：应用初始化、扩展注册、模型、业务逻辑、Blueprint 路由都比较集中。这样一开始开发很快，但业务一多就会出现几个问题。第一，Blueprint 很容易业务膨胀，路由函数里会同时处理参数、权限、数据库、通知和响应拼装。第二，ORM 和 Flask 扩展会不断向业务层泄漏，导致服务边界不清。第三，测试和后续扩展会越来越困难，尤其是不利于做可插拔能力。

所以我做的核心重构，不是换框架，而是重新划分职责边界。现在最外层还是 Flask，但它更多只是协议适配层。接口层放在 `app/api` 和 `app/auth`，主要负责接收请求、做鉴权、调用 service。业务编排收敛到 `app/services`，比如登录、发帖、评论、通知这些完整用例都在那里。领域规则和抽象接口放在 `app/domain`，包括 policy、repository interface、各种 port，还有 unit of work 抽象。再往下是 `app/infrastructure`，专门放 SQLAlchemy 仓储实现、JWT 适配器、Redis、Celery、Qiniu 这类基础设施。

这里最关键的设计点有三个。

第一个是依赖倒置。比如 `PostService` 并不直接依赖 SQLAlchemy，也不直接调 Flask-JWT 或七牛 SDK，它依赖的是 `UnitOfWork`、`NotificationDispatcherPort`、`ResponseAssemblerPort` 这些抽象。低层实现再去实现这些接口。

第二个是事务和数据访问边界清晰了。现在是 `Service -> UnitOfWork -> Repository -> ORM` 这条链路，而不是路由里直接 `db.session.commit()`。

第三个是把 Presenter 也抽出来了。很多项目会忽略这一层，但这个项目把前端需要的 JSON 映射放进了 assembler，避免 service 里直接手写响应结构。

如果拿发帖这个流程举例，它现在是：HTTP 请求先进入 `posts.py` 的控制器，控制器调用 `PostService.create_post()`，service 负责做内容校验、摘要生成、事务提交、通知关注者，再由 repository 落到 SQLAlchemy，最后 assembler 再把结果映射成前端结构。这样每一层职责都比较清晰。

我觉得这个项目真正能体现架构能力的地方，不是“用了 Flask + Redis + Celery”，而是我把一个原本容易长成大泥球的 Flask 项目，拆成了协议层、用例层、领域层、基础设施层，让它后面更容易测试、更容易替换实现，也更容易往插件化方向继续演进。


## 8 分钟版

如果让我详细展开这个项目，我一般会从“为什么要重构、重构成什么样、解决了什么问题”这三层来讲。

第一层是为什么要重构。

这个项目原来的结构其实很典型，就是 Flask 项目早期最常见的单体写法。应用初始化、扩展对象、模型、路由、部分业务逻辑都比较集中。这个阶段的优点是开发效率高，但随着用户、文章、评论、通知、聊天这些模块越来越多，结构问题就开始暴露出来了。

最明显的问题是 Blueprint 业务膨胀。因为路由是所有请求的天然入口，所以最容易不断往里塞逻辑。刚开始只是接个参数，后面会慢慢塞权限判断、ORM 查询、事务处理、发通知、拼 JSON、打日志，最后一个接口函数既像 controller，又像 service，还顺手做了 repository 和 presenter 的工作。这样写短期看很直接，但长期维护成本很高。

第二个问题是框架和 ORM 对业务侵入太深。比如业务代码很容易直接依赖 Flask 全局对象、SQLAlchemy session、Redis、JWT 扩展。这会导致业务逻辑离不开运行时框架环境，单元测试就很难写，后面如果想替换实现，比如换一种通知方式、换一种存储方式，也会牵一发动全身。

第三个问题是不利于可插拔和演化。虽然这个项目现在还不是完整插件系统，但如果业务、路由、模型、基础设施全部写死在一起，那后面不管是做模块化、插件化，还是做能力替换，都会非常痛苦。

所以第二层就是，我把它重构成什么样。

现在这个项目本质上还是 Flask 应用，但 Flask 的角色被压缩成了“应用壳”和“协议适配层”。应用启动在 `create_app()` 里完成，它主要负责加载配置、初始化基础设施、组装依赖容器、注册 Blueprint 和错误处理。真正的业务逻辑不再以 Flask 为中心。

接口层主要在 `app/api` 和 `app/auth`。这一层的职责很清楚，就是接请求、做鉴权、读参数、调 service、返回统一响应。它不应该直接写复杂业务，更不应该直接操作各种底层实现。

业务编排层在 `app/services`。这一层最像 Clean Architecture 里的 use case。比如 `PostService` 负责发帖、查帖、编辑帖子；`AuthService` 负责登录、注册、邮箱验证码、密码修改；其他还有评论、点赞、通知、聊天等服务。这里的重点是 service 负责编排业务流程，而不是依赖某个具体框架。

领域层在 `app/domain`。这里放了几类关键内容。第一类是 policies，也就是业务规则，比如发帖内容怎么校验、帖子类型怎么归一化、摘要怎么生成。第二类是 repository interface，也就是业务需要什么数据访问能力，但不关心怎么实现。第三类是 ports，比如 JWT、通知、存储、配置、在线状态这些外部能力接口。第四类是 unit of work 抽象，用来表达事务边界。

基础设施层在 `app/infrastructure`。这里去实现前面那些抽象，包括 SQLAlchemy 仓储实现、JWT 适配器、Redis 适配器、Qiniu 存储、Celery 通知派发、SocketIO 服务等。也就是说，高层定义规则和接口，低层负责接真实世界。

这个结构里我觉得最值得讲的第一个点，是依赖倒置。

比如 `PostService` 并不直接 import SQLAlchemy session，也不直接调 Flask 扩展。它依赖的是 `UnitOfWork`、`ResponseAssemblerPort`、`NotificationDispatcherPort`、`HotPostsService` 这些抽象或稳定服务。这样高层业务只表达“我要完成一个发帖用例”，并不关心底层到底用什么技术细节实现。SQLAlchemy 仓储、Celery 通知、JWT 库这些低层实现，反过来适配高层抽象。这就是 Clean Architecture 里最核心的思想之一。

第二个值得讲的点，是 Repository 和 UnitOfWork 的组合。

很多 Flask 项目会在路由里直接 `Model.query`，然后 `db.session.commit()`。这个项目现在改成了 `Service -> UnitOfWork -> Repository -> ORM` 的链路。Repository 负责数据访问能力，UnitOfWork 负责事务提交、回滚、flush。这样做的好处是业务流程和数据访问细节被分开了，而且事务边界更清晰。

比如发帖流程里，service 先校验内容，再创建 post，接着 `flush()` 拿到 post.id，然后创建图片实体，最后统一 `commit()`。提交成功以后再去派发关注者通知。这条链路如果直接写在路由里，代码会非常散，而且事务语义也不清楚。

第三个值得讲的点，是 Presenter 单独抽离。

这一点很多人会忽略，但我认为它很重要。因为前端真正需要的数据结构，和 ORM 实体结构通常不是一回事。如果 service 里直接拼 JSON，久而久之 service 会变成半业务半表现层的混合体。这个项目把映射工作放在 assembler 里，比如帖子、用户、评论、通知的返回结构都由 presenter 负责整理，这样 service 只关心业务结果，不关心 API 细节。

第四个点是这个项目对“插件化”的处理要实事求是地讲。

我不会说它已经是一个成熟插件架构，因为目前没有看到标准的插件目录、manifest、动态扫描、热插拔、运行期启停这些能力。它的路由注册依然是静态的，Blueprint 也是启动时直接注册。

但我会说，它已经具备了插件化的底座。为什么？因为它已经把关键能力抽象成 port 和 interface，又用 dependency injector 做了统一装配。也就是说，未来如果要做真正的插件系统，已经有了最难的一步，就是高层业务不再直接依赖低层实现，而是依赖抽象。后面要补的是插件发现、生命周期管理、动态注册和启停机制。

如果面试官让我举一个完整调用链，我一般会讲发帖。

发帖请求先进入控制器 `PostGroupApi.post()`。控制器只做几件事：鉴权、参数读取、调用 service、失效缓存、再返回统一响应。真正的业务编排在 `PostService.create_post()`。在那里会先做内容校验和帖子类型归一化，然后调用 domain policy 生成摘要，再通过 unit of work 调用 post repository 创建帖子。中间先 flush 拿到主键，再创建关联图片，最后 commit。提交成功后，再通过通知端口派发新帖子通知给关注者。然后接口层再去刷新帖子列表缓存，最终由 assembler 把帖子列表转换成前端要的字段结构返回。

这个链路能说明几个问题：第一，controller 没有业务膨胀；第二，service 才是业务主脑；第三，repository 负责数据访问；第四，presenter 负责返回结构；第五，通知、缓存、热榜这些横切能力没有直接塞进控制器。

最后如果让我总结这个项目真正的技术价值，我会说，它的价值不在于单点技术，而在于工程演化能力。

普通 CRUD 项目只要能把接口跑通就行，但这个项目在往更复杂的后端场景发展，它同时有 HTTP、WebSocket、异步通知、缓存、热榜、第三方登录、文件存储这些能力。如果没有清晰的分层和依赖边界，后面一定会越来越难维护。

我在这个项目里最想体现给面试官看的，不是“我会写 Flask 接口”，而是三件事。

第一，我能识别单体 Flask 项目为什么会逐步失控。

第二，我能把它拆成 controller、service、domain、repository、infrastructure 这些稳定边界，而且不是纸上谈兵，而是落到了真实代码里。

第三，我知道什么叫真正的架构收益。不是目录好看，而是测试更容易、实现更容易替换、横切能力更容易接入、系统更容易往插件化和模块化继续演进。

如果最后要用一句话收尾，我会这么说：

这个项目本质上是一次从“以 Flask 和 ORM 为中心的单体写法”，走向“以用例、抽象和依赖倒置为中心的工程化后端结构”的重构实践。它不一定是最纯粹的 Clean Architecture，但它已经解决了真实项目里最关键的几个问题：业务膨胀、框架侵入、数据访问耦合、测试困难，以及后续演化空间不足。
